## Модель: что означают строки кода

`class Project extends Model` — проект использует Eloquent ORM Laravel. ORM позволяет работать с БД через объекты: `Project::create(...)`, а не писать INSERT вручную. По соглашению Project соответствует projects.

`$fillable = ['name', 'description', 'user_id']` — эти поля можно передавать в массовое заполнение. Это ограничение полей, а не проверка прав пользователя.

`owner(): BelongsTo` — один проект принадлежит одному User. `user_id` хранит id владельца. `$project->owner->name` получает имя владельца.

`tasks(): HasMany` — у проекта много задач. `$project->tasks` возвращает связанные задачи. Саму модель Task готовил участник 3.

## Миграция: как устроена таблица

| Поле | Значение |
|---|---|
| id | Уникальный номер проекта |
| name | Название, обязательное |
| description | Описание; допускает NULL |
| user_id | Внешний ключ на users.id, владелец |
| created_at | Время создания |
| updated_at | Время последнего изменения |

`up()` создаёт таблицу, `down()` удаляет её при откате миграции. `constrained()` добавляет внешний ключ, не позволяющий сослаться на несуществующего владельца. `cascadeOnDelete()` на user_id означает, что удаление владельца удаляет его проекты. Удаление проекта также удаляет задачи из-за внешнего ключа в миграции задач, а дальше каскадно удаляются комментарии.

**Модель — способ работы с данными в PHP; миграция — описание структуры БД. Это не одно и то же.**

## Контроллер: семь методов CRUD

CRUD = Create, Read, Update, Delete — создание, чтение, изменение, удаление.

| Метод | Когда вызывается | Что делает |
|---|---|---|
| index | GET /projects | Проверяет viewAny, получает проекты с владельцами и числом задач; сортирует новые первыми; выводит по 10 на странице |
| create | GET /projects/create | Проверяет create и показывает форму |
| store | POST /projects | Получает проверенные поля, проверяет create, создаёт проект и отправляет на его страницу |
| show | GET /projects/{project} | Проверяет view, загружает владельца и задачи с исполнителями, показывает карточку |
| edit | GET /projects/{project}/edit | Проверяет update, показывает форму редактирования |
| update | PUT/PATCH /projects/{project} | Проверяет update, сохраняет проверенные name/description |
| destroy | DELETE /projects/{project} | Проверяет delete, удаляет проект, возвращает к списку |

Маршруты созданы одной строкой `Route::resource('projects', ProjectController::class)` в [routes/web.php](https://github.com/amr1ds/task-manager/blob/28bcb55/routes/web.php). Этот файл подготовил участник 1; по заданию вы его не меняли. Маршруты находятся внутри middleware auth: незарегистрированный в сессии посетитель перенаправляется на вход.

`Project $project` в аргументах — привязка модели к маршруту: Laravel находит проект по id из URL. Если записи нет, возвращает 404.

`with('owner')` загружает владельцев заранее; `withCount('tasks')` получает количество задач; это сокращает дополнительные запросы на каждой строке. `latest()` сортирует по дате создания, `paginate(10)` разбивает на страницы.

## Кто что может

- Все вошедшие пользователи могут смотреть проекты.
- Администратор и менеджер могут создавать проекты.
- Администратор может изменять и удалять любой проект.
- Владелец может изменять и удалять свой проект.
- Обычный исполнитель не может создать проект или изменить чужой.

Точная формула update/delete: `isAdmin() || user.id === project.user_id`. В ней нет проверки роли manager. Поэтому если создателя позже понизят до executor, он сохранит права владельца. На вопрос о таком случае отвечайте именно так — это ограничение текущей реализации.

Policy проверяется в контроллере через `$this->authorize(...)`. `@can` в Blade скрывает кнопки, но скрытая кнопка сама по себе не защищает от ручного HTTP-запроса. Серверная проверка обязательна.

## Пошаговый пример — пользователь нажал «Создать»

1. Открыл `/projects/create`; auth проверил вход, Policy проверила роль.
2. Контроллер вернул create.blade.php с полями из _form.blade.php.
3. Пользователь ввёл название и описание; браузер отправил POST /projects.
4. CSRF-токен защищает запрос. StoreProjectRequest проверяет поля до выполнения store.
5. В store вызывается authorize; затем Project::create получает проверенные поля.
6. **user_id берётся из `$request->user()->id`.** Присланный клиентом чужой user_id не используется.
7. В БД появляется запись; браузер перенаправляется на её карточку; выводится «Проект создан».

При неправильном названии запись не сохраняется, форма показывает ошибку. При недостаточных правах сервер отвечает 403. При отсутствии проекта — 404. Ошибка 500 относится к внутреннему сбою, а не к обычному отказу Policy.

## Как читать Blade

`@extends('layouts.app')` использует общий дизайн друга. `@section` задаёт содержимое страницы. `@include('projects._form')` вставляет поля формы. `{{ $project->name }}` выводит название с экранированием HTML. `old('name')` сохраняет введённое значение после ошибки. `@error('name')` показывает сообщение проверки. `@csrf` добавляет защитный токен. `@method('PATCH')` и DELETE позволяют HTML-форме POST обозначить нужный метод Laravel.

## Вопросы преподавателя

**Зачем отдельные StoreProjectRequest и UpdateProjectRequest?** Чтобы правила форм были отделены от действий контроллера; сейчас они одинаковые, но могут развиваться независимо.

**Почему authorize() в этих Request возвращает true?** Потому что права проверяются в контроллере через Policy. Комментарий про authorizeResource в StoreProjectRequest устарел: фактически используются явные authorize-вызовы.

**Можно подменить владельца в форме?** При создании — нет: контроллер берёт id из авторизованного пользователя. При обновлении Request допускает только name/description, поэтому user_id не попадает в validated().

**Чем create отличается от store?** create показывает форму GET-запросом, store сохраняет данные POST-запросом. Аналогично edit показывает форму, update изменяет запись.

**Зачем пять представлений, а не одно?** У списка, карточки, создания и редактирования разные задачи; повторяющиеся поля вынесены в _form.

**Почему проект удаляется вместе с задачами?** Это задаётся внешним ключом tasks.project_id с cascadeOnDelete в миграции задач. Контроллер просто вызывает delete у проекта.

**Может исполнитель видеть чужие задачи?** В отдельном модуле задач доступ ограничен, но текущая карточка проекта выводит сведения обо всех задачах проекта. Это найденный недостаток: если требуется полная изоляция, связь tasks нужно фильтровать по правам.

**Что сделали лично по заданию?** Перенесли 11 файлов модуля проектов из выданного архива, оформили модель/миграцию, Policy и CRUD отдельными ветками и PR. Не утверждайте, что написали с нуля то, что было дано готовым.
